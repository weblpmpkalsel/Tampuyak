# M2.2 SCHOOL KNOWLEDGE DOMAIN | AUDIT REPORT

## 1. Enterprise Change Gate
This sprint is authorized ONLY to redefine and expand the conceptual model of the "School Knowledge Domain" (currently represented as `SchoolContextKnowledgePayload`). The goal is to accurately classify school data into independent enterprise sub-domains. Everything else, including Front Matter, Regulatory Knowledge, and the Canonical Renderer, remains strictly LOCKED.

## 2. Boundary Audit
- **Renderer**: Untouched. Remains a pure consumer of Canonical Documents.
- **Publishing & Backup**: Untouched.
- **Planning (RKJM, RKT, RKAS)**: Untouched.
- **Workspace**: Untouched.
- **Front Matter & Regulatory Knowledge**: Untouched. Boundaries are strictly preserved.

## 3. Knowledge Domain Audit
The School Knowledge Domain represents the physical and sociological reality of the school, entirely independent of the KSP document. 
Independent knowledge categories identified:
- Profile Identity Knowledge
- Learner Characteristics Knowledge
- Human Resources / Educator Knowledge
- Infrastructure & Facilities Knowledge
- Community & Partnership Knowledge
- Cultural & Environmental Knowledge
- Governance & Accreditation Knowledge

## 4. Knowledge Classification Audit
- **School Profile Knowledge**: Foundational identity (NPSN, Name, Address, Status).
- **Learner Knowledge**: Student demographics, learning styles, dominant needs, clinical barriers.
- **Human Resources Knowledge**: Teacher qualifications, leadership hierarchy, capacity.
- **Infrastructure Knowledge**: Facilities, internet bandwidth, specialized labs.
- **Partnership Knowledge**: Parent communities, industry linkages (DUDI).
- **Cultural Knowledge**: Local wisdom, prevailing regional characteristics.
- **Governance Knowledge**: Accreditation status, governing body.

## 5. Knowledge Ownership Audit
- **Workspace (Current)**: Temporarily acts as the owner and conduit via User Input/Metadata.
- **Government / Dapodik (Future)**: The true authoritative owner of Profile, HR, and Infrastructure Knowledge.
- **Local Assessments (Future)**: The true owner of Learner and Cultural Knowledge.
- **School Knowledge Registry (Future)**: Will act as the enterprise cache and system of record for all these external sources.

## 6. Knowledge Source Audit
- Profile & Infrastructure: Originates from the Dapodik system (currently mocked via Workspace Metadata).
- Learner & Cultural: Originates from psychological/diagnostic assessments (currently mapped from Workspace).
- Partnership: Originates from manual school deliberation.
No data is invented by the Builder; all data originates from upstream sources.

## 7. Knowledge Independence Audit
Each sub-domain can evolve independently. If a school constructs a new library, only the `InfrastructureKnowledge` changes. If a new student cohort arrives, only `LearnerKnowledge` changes. One changing does not invalidate the others. The Assembler simply pulls the latest version of each independent domain.

## 8. Builder Audit
Builders remain strict Consumers. The `KspBab1Structure` Builder will receive the composed School Knowledge and map it directly to `PARAGRAPH`, `HEADING`, and `LIST` blocks. It will never calculate ratios, infer conclusions, or generate AI summaries of the school's state.

## 9. Assembler Audit
The `KspDocumentAssembler` operates as the pure orchestrator:
1. Fetches/Constructs `RegulatoryKnowledgePayload`.
2. Fetches/Constructs the expanded `SchoolKnowledgePayload` (containing Profile, Learners, Infrastructure, etc.).
3. Injects both discrete payloads into the BAB I Builder: `buildKspBab1Section(schoolKnowledge, regulatoryKnowledge)`.

## 10. Knowledge Registry Audit
**Future School Knowledge Registry Design**:
- **Registry Layer**: Exposes standardized endpoints (`getLearnerKnowledge()`, `getInfrastructureKnowledge()`).
- **Knowledge Objects**: Returns strongly-typed sub-domain payloads.
- **Assembler**: Queries the Registry, composes the unified `SchoolKnowledgePayload`, and passes it down.
- **Builder**: Remains completely oblivious to the Registry, consuming the exact same payload it does today.

## 11. Files To Modify
If authorized to implement the expanded data model:
- `src/enterprise/knowledge/builders/SchoolContextBuilder.ts` (To expand the interfaces)
- `src/enterprise/document/ksp/KspDocumentAssembler.ts` (To map the expanded data)
- `src/enterprise/document/ksp/bab1/KspBab1Structure.ts` (To handle interface renames if requested)

## 12. Risk Assessment
- **Architecture Risk**: **LOW**. Merely expanding the type safety of an existing payload.
- **Knowledge Risk**: **LOW**. Explicitly separating concerns (Learners vs Infrastructure).
- **Government Fidelity Risk**: **LOW**. Passthrough data without AI distortion.
- **Regression Risk**: **LOW**. As long as existing fields in `SchoolContextKnowledgePayload` are safely preserved or migrated.
- **Future Registry Risk**: **LOW**. Perfectly models the exact contract the future Registry must fulfill.

# PRE-IMPLEMENTATION RECOMMENDATION: DOMAIN RENAMING

## Analysis
The user requested evaluating a rename from `SchoolContextKnowledgePayload` to `SchoolKnowledgePayload` to reflect an Enterprise Domain rather than just "context."

The payload is currently defined in `SchoolContextBuilder.ts`, relying on `SchoolContextBuilderInput` and `SchoolContextService`.

## Recommendation: DEFER AS TECHNICAL DEBT
I recommend **deferring** the semantic rename for this sprint and logging it as Technical Debt for the upcoming Enterprise Knowledge Layer migration.

### Justification
1. **Semantic Cascading**: Renaming *only* the payload to `SchoolKnowledgePayload` while leaving the builder named `SchoolContextBuilder` and the underlying service named `SchoolContextService` creates a semantic mismatch within the domain layer.
2. **Chain Reaction**: To do this cleanly, we would need to rename multiple files and service interfaces (`SchoolContextBuilder.ts` -> `SchoolKnowledgeBuilder.ts`, `SchoolContextService` -> `SchoolKnowledgeService`).
3. **Zero Regression Priority**: The prompt strictly states "Zero Regression has higher priority." Renaming underlying services and files to maintain semantic consistency constitutes refactoring unrelated code and introduces unnecessary regression risk at this exact checkpoint.

### Proposed Action
- **Do not execute the rename** during this sprint.
- **Log Technical Debt**: Add a formal technical debt note that `SchoolContext*` terminology must be migrated to `SchoolKnowledge*` when the true School Knowledge Registry is built.
- **Proceed** with expanding the core School Knowledge data structures using the existing `SchoolContextKnowledgePayload` nomenclature to guarantee zero regression on the current locked architecture.
