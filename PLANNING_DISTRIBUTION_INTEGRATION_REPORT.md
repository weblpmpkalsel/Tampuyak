# RKJM ENGINE PHASE 2.5.1 - PLANNING DISTRIBUTION INTEGRATION

## 1. Architecture Review
The previous data pipeline hardcoded all generated activities into `annualPlans.Y1`. The `OperationalPlanningEngine` has now been extended with the `PlanningDistributionService`. This service encapsulates the responsibility for distributing activities across planning years (`Y1`, `Y2`, `Y3`, `Y4`), ensuring that multi-year planning is robust and completely separate from execution logic.

## 2. Current annualPlans Flow
- **Input**: Extracted/Generated activities and budgets.
- **Transformation**: Iterate over `newObjectives` and push 100% of generated `rktY1`, `rkasY1`, `implementation`, `monitoring`, and `evaluation` data into `annualPlans["Y1"]`.
- **Output**: Multi-year buckets `Y2`, `Y3`, `Y4` remain structurally empty, causing downstream document builders (like Chapter 4) to only see and render "Tahun Ke-1" data.

## 3. New annualPlans Flow
- **Input**: Same extracted/generated activities and budgets.
- **Transformation**: Before pushing data, the `annualPlans` pipeline invokes `PlanningDistributionService.assignYearToActivity(rktId, index)`. 
- **Output**: The activities and corresponding execution data (RKAS, implementation, monitoring, evaluation) are pushed into their correct `annualPlans[targetYear]` bucket. Activities are now appropriately distributed across `Y1`, `Y2`, `Y3`, and `Y4`. 

## 4. PlanningDistributionService Responsibilities
- **Read-Only Engine Consumer**: Reads the explicit distributions from `OperationalPlanningEngine`.
- **Deterministic Distribution**: If a distribution is not yet explicitly registered in the engine, it performs a fallback deterministic assignment (e.g. round-robin via modulo `index % 4 + 1`) to ensure activities are distributed across 4 years instead of defaulting to Year 1.
- **Output**: Returns a strict type of `'Y1' | 'Y2' | 'Y3' | 'Y4'`.

## 5. Integration Diagram
```text
KnowledgeGraph (SSOT)
       ↓
AnnualPlanningEngine (Operational Generation)
       ↓
PlanningDistributionService (Orchestration Layer) --> assignYearToActivity(id)
       ↓
annualPlans Generator (Tampuyak UI & Sync Engine)
       ↓
annualPlans.Y1 | annualPlans.Y2 | annualPlans.Y3 | annualPlans.Y4
       ↓
Chapter4Builder (Document Generation Layer)
```

## 8. Backward Compatibility Analysis
- `annualPlans.Y1` retains its exact structural format. Any component directly reading `Y1` (such as legacy Dashboard or RKAS components) will continue working exactly as before, albeit with a smaller subset of activities (only those scheduled for Y1).
- The `PlanningDistributionService` defaults to returning `Y1` to `Y4`, which exactly matches the keys generated by the pipelines. 

## 9. Risk Analysis
- **Data Integrity Risk**: Extremely low. The structures themselves were not altered; only the array destination key was updated via the distribution service.
- **Presentation Layer**: Since the downstream data structure is unaltered, components depending on `annualPlans` will seamlessly display the correct multi-year distributed data. 
- **Next Phase Readiness**: `Chapter4Builder` is now fully ready to be reconstructed to read from all 4 years, as they are genuinely populated.
