# Enterprise Deployment Forensic Report

## 1. Verify that the latest source code is actually included in the deployed bundle
The local workspace `dist/` directory was verified by searching for the string `remixed-api-key`. The search returned zero results. This confirms that the local production build generated by Vite successfully stripped out all fallback placeholders. If the deployed bundle on Cloud Run still exhibits the issue, it means the deployed bundle does not match the latest local source code. Either the latest code was not successfully deployed to the remote server, or the user has not triggered a new deployment since the fix was applied.

## 2. Verify whether Service Worker is serving stale assets
The application is configured as a Progressive Web App (PWA) using `vite-plugin-pwa` with `registerType: 'prompt'` and Workbox.
When a new version of the application is deployed, the Service Worker downloads the new assets in the background but **does not apply them automatically**. It continues to serve the old cached `index.html` and JavaScript chunks until the user explicitly clicks the "Muat Ulang" (Refresh) button in the `EnterpriseUpdateManager` prompt, or manually clears the site data. If the user hasn't clicked refresh, their browser is executing the stale cached bundle containing the old Firebase configuration.

## 3. Verify whether another Firebase initialization file still exists
A search for `initializeApp` across the entire `src/` directory confirms that `src/lib/firebase.ts` is the **only** file that initializes Firebase. No secondary or shadow initialization files exist.

## 4. Search the ENTIRE repository for specific keywords
- **`remixed-api-key`**: Only exists in `firebase-applet-config.json` (as a placeholder) and in audit markdown reports. It does NOT exist anywhere in `src/` or `dist/`.
- **`defaultFirebaseConfig`**: Only exists in audit reports. The import was successfully removed from `src/lib/firebase.ts`.
- **`AIza`**: Only found in old audit reports (`FIREBASE_AUDIT.md`) and scripts (`query_user.cjs`). Not present in source code.
- **`initializeApp`**: Found exactly twice in `src/lib/firebase.ts` (the import statement and the invocation).

## 5. Verify which firebaseConfig object is actually imported by authService
`src/services/auth/authService.ts` does NOT import `firebaseConfig` directly. Instead, it imports the already-initialized `auth` instance from `src/lib/firebase.ts` (`import { auth } from '../../lib/firebase';`).
The `auth` instance is created using `getAuth(app)`, where `app` is initialized using the strict, environment-variable-only `firebaseConfig` object defined in the fixed `src/lib/firebase.ts`.

## 6. Compare local build vs deployed build
- **Local Build (`dist/`)**: The local bundle enforces strict environment variable validation (`throw new Error(...)`) and contains absolutely no trace of `remixed-api-key` or `firebase-applet-config.json`.
- **Deployed Build (Browser)**: Because the browser is still making network requests to `identitytoolkit.googleapis.com/...key=remixed-api-key`, it is mathematically impossible for the browser to be executing the local build. The browser is executing an old bundle.

## CONCLUSION: Why is production still using `remixed-api-key`?
The root cause is a **Caching / Deployment Desync**. 
The source code is completely fixed, but the browser is executing the old version of the code because of one or both of the following reasons:
1. **PWA Stale Cache**: The browser's Service Worker is aggressively caching the old JavaScript bundle. The user must click the "Muat Ulang" button on the update banner or hard refresh / clear site data to load the new bundle.
2. **Missing Deployment**: The fixed source code resides in the local AI Studio workspace, but the "Shared App URL" (Cloud Run instance) has not been updated with the new code (the user needs to re-trigger the Share/Deploy action to build a new container).
