# W1.4 PROGRESSIVE WORKSPACE MIGRATION

## 1. MIGRATION STRATEGY
The migration will follow a **Strangler Fig** application pattern, ensuring zero disruption to existing legacy systems (RKJM, RKT, RKAS). 
Instead of attempting a risky, massive refactor of the existing monolithic `DataSekolahView`, we will introduce parallel "Enterprise Workspaces" tailored specifically for the KSP Gold requirements. 
- The **Current Workspace (`DataSekolahView`)** will be frozen in its current state. It will continue to act as the primary configuration hub for RKJM, RKT, and RKAS.
- The **New Enterprise Workspace** will be introduced via dedicated entry points (e.g., `Pengorganisasian Pembelajaran`, `Evaluasi & Tindak Lanjut`). These new UI hubs will bind to new, isolated segments of the global state (e.g., `settings.curriculum`, `settings.evaluation`) and serve **only KSP Gold**.

## 3. FUTURE MIGRATION PLAN
1. **Phase 1: Coexistence (Current Phase)** - Build the new KSP Gold features in isolated Enterprise Workspaces. KSP Gold reads from both the legacy state (for School Profile via Adapter) and the new Enterprise state (for Curriculum/Evaluation). RKJM/RKT/RKAS remain strictly bound to legacy state.
2. **Phase 2: Adapter Routing** - Route RKJM/RKT/RKAS state queries through intermediate adapters that can read from either the legacy state or the new Enterprise state.
3. **Phase 3: State Migration** - Run a one-time migration to move legacy `DataSekolah` data into the new Enterprise state shape.
4. **Phase 4: Sunsetting** - Deprecate the old `DataSekolahView` and point all documents exclusively to the Enterprise Workspaces.

## 4. RISK ASSESSMENT
- **State Fragmentation:** High risk of duplication. If a user enters "Extracurriculars" in the new workspace but expects it to update in a legacy tab, they may be confused.
  *Mitigation:* Clearly label the new Enterprise Workspaces as specific to KSP (or use specific terminology), and do not duplicate fields that already exist in the legacy view. The `KspMetadataAdapter` will continue bridging the gap for shared fields (like Vision/Mission).
- **Maintenance Overhead:** Developers must maintain two UI patterns simultaneously.
  *Mitigation:* Keep the new Enterprise Workspace highly modular and strictly typed, ensuring it acts as the canonical reference for future development.

## FINAL DECISION
**GO**

The Progressive Workspace Migration architecture provides a safe, non-destructive path to scale KSP Gold without risking the stability of RKJM, RKT, and RKAS.
