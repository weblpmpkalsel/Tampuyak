# W3.0 ENTERPRISE DOCUMENT LIBRARY (EDL) ARCHITECTURE

## 1. ENTERPRISE VISION
The Enterprise Document Library (EDL) is the official repository for every reusable school document across the Enterprise Platform. It moves beyond passive file storage to active **School Knowledge Management**. Every document becomes a reusable Enterprise Asset. 

**Core Principle:** "Never ask the school to upload what the system can help them create."

## 2. REPOSITORY ARCHITECTURE
The repository is completely decoupled from any specific enterprise module (e.g., KSP, RKJM) and uses a robust metadata schema to manage assets without hardcoding document types.

**Document Metadata Schema:**
- `id`: Unique identifier (UUID).
- `title`: Human-readable name.
- `category`: Classification (dynamic list, not hardcoded).
- `knowledgeDomain`: Pedagogical, Administrative, Financial, etc.
- `owner`: User or role responsible for the document.
- `academicYear`: The applicable academic cycle.
- `version`: Current version identifier.
- `status`: Lifecycle state (`Draft`, `Reviewed`, `Approved`, `Archived`).
- `source`: Origin (`Official Template`, `Generated`, `Uploaded`, `Copied`).
- `createdDate` / `updatedDate`: Timestamps.
- `usedBy`: Array of module identifiers referencing this document.
- `description`: Contextual summary.

## 3. KNOWLEDGE PACK ARCHITECTURE
Documents and templates are organized into Knowledge Packs to separate official guidelines from local school intellectual property.
- **Official Knowledge Pack:** Maintained centrally (e.g., Kemendikdasmen 2026, BPMP, BSKAP). Contains immutable, highly compliant templates.
- **School Knowledge Pack:** Maintained locally by the school (e.g., SDN XXX). Contains their specific approved documents and custom templates.
- **Future Community Pack:** Enables schools to share exemplary documents across the platform.

## 4. TEMPLATE ENGINE
The Template Engine provides standardized baselines across the platform.
- **Official Templates:** Read-only structures provided by the Official Knowledge Pack.
- **Editable Templates:** Cloned from official templates for local customization.
- **School Templates:** Custom formats created and saved by the school.
- **Future Shared Templates:** Templates distributed via the Community Pack.

## 5. REFERENCE ENGINE
Documents are treated as single sources of truth.
- The Reference Engine manages connections between EDL assets and consuming modules (KSP, RKJM, RKT, RKAS, Supervision, SPMI, Adiwiyata).
- **No duplication:** Modules reference the Document ID, not a physical file.
- `usedBy` tracking prevents accidental deletion of actively referenced documents.

## 6. DOCUMENT WIZARD
Instead of merely offering upload functionality, the EDL provides a guided creation experience.
- Interactive, structured questionnaires mapped to template variables.
- Generates an **editable draft**, allowing the school to remain fully responsible for the final content.
- No automatic publishing; human review is mandatory.

## 7. AI STRATEGY
The architecture reserves integration points for future AI capabilities without implementing them in this phase:
- **Draft generation:** Pre-filling wizard responses based on school context.
- **Policy suggestions:** Recommending clauses based on the latest regulations.
- **Compliance checking:** Automated rubric scanning of uploaded or drafted documents.
- **Document comparison:** Semantic diffs between versions.
- **Revision assistance:** Highlighting areas for improvement.

## 8. GOVERNMENT FIDELITY STRATEGY
Every official template and wizard flow is designed to adhere strictly to the latest national standards:
- **Kemendikdasmen 2026** and **BSKAP** guidelines.
- Support for the **Deep Learning Policy**.
- Integration of **8 Dimensi Profil Lulusan** and **7 Kebiasaan Anak Indonesia Hebat**.
- **Template Versioning:** The architecture supports versioning templates seamlessly whenever government regulations change, ensuring older documents remain intact while new documents use the updated standards.

## 9. MIGRATION STRATEGY
- **Phase 1:** Implement the EDL Core, Metadata Service, and Attachment Gateway.
- **Phase 2:** Migrate legacy file uploads to the new metadata schema, assigning Document IDs.
- **Phase 3:** Introduce the Template Engine, Knowledge Packs, and Document Wizard.
- **Phase 4:** Update all Enterprise Modules (KSP, RKJM, etc.) to use the Reference Engine exclusively.

## 10. RISK ASSESSMENT
- **Risk:** Complex referencing leading to orphaned data or dead links.
  - **Mitigation:** Strict referential integrity in the Reference Engine; soft-delete (archive) instead of hard delete for referenced items.
- **Risk:** Template obsolescence due to rapid policy changes.
  - **Mitigation:** Template versioning and the Official Knowledge Pack structure allow non-destructive updates to government guidelines.
- **Risk:** User confusion over the wizard vs. upload choice.
  - **Mitigation:** Clear UX pathways prioritizing "Create from Template/Wizard" as the primary action, with "Upload Existing" as a secondary fallback.

## 11. ADR-010: ENTERPRISE DOCUMENT LIBRARY
**Context:** The platform requires a centralized, reusable, and intelligent way to manage documents across various enterprise modules (KSP, RKJM, RKAS, etc.) without hardcoding document types or relying solely on passive file uploads.
**Decision:** Implement the Enterprise Document Library (EDL) using a metadata-driven approach with Knowledge Packs, a Reference Engine, and a Document Wizard.
**Consequences:** 
- Eliminates document duplication.
- Enforces single-source-of-truth references via Document IDs.
- Future-proofs the system for AI integration and policy shifts via template versioning.

## FINAL DECISION
**GO**

The Enterprise Document Library architecture successfully provides a scalable, type-agnostic, and highly reusable foundation for all document operations across the platform, fully eliminating the reliance on scattered uploads and hardcoded document types.
