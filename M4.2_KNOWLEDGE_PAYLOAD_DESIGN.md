# KSP GOLD M4.2: BAB IV KNOWLEDGE PAYLOAD DESIGN

## 1. PAYLOAD STRUCTURE & INTERFACE HIERARCHY
The `Bab4KnowledgePayload` is the single, immutable input for the BAB IV Builder. It aggregates several independent knowledge domains.

```typescript
export interface Bab4KnowledgePayload {
  readonly implementationSupport: ImplementationSupportDomain;
  readonly monitoring: MonitoringDomain;
  readonly evaluation: EvaluationDomain;
  readonly reflection: ReflectionDomain;
  readonly followUp: FollowUpDomain;
  readonly professionalDevelopment: ProfessionalDevelopmentDomain;
}

export interface ImplementationSupportDomain {
  readonly programs: ReadonlyArray<{
    readonly programName: string;
    readonly objective: string;
    readonly targetAudience: string;
    readonly frequency: string;
  }>;
}

export interface MonitoringDomain {
  readonly activities: ReadonlyArray<{
    readonly activityName: string;
    readonly method: string;
    readonly indicator: string;
    readonly schedule: string;
  }>;
}

export interface EvaluationDomain {
  readonly frameworks: ReadonlyArray<{
    readonly aspect: string;
    readonly evaluationMethod: string;
    readonly expectedOutcome: string;
  }>;
  readonly latestRaporEducationSummary: string;
}

export interface ReflectionDomain {
  readonly mechanisms: ReadonlyArray<{
    readonly stakeholder: string;
    readonly method: string; // e.g., Focus Group Discussion, Survey
    readonly frequency: string;
  }>;
}

export interface FollowUpDomain {
  readonly strategies: ReadonlyArray<{
    readonly issue: string;
    readonly plannedAction: string;
    readonly integrationTarget: string; // e.g., RKT, RKJM
  }>;
}

export interface ProfessionalDevelopmentDomain {
  readonly trainingPlans: ReadonlyArray<{
    readonly programName: string;
    readonly competenciesTargeted: string;
    readonly participantRole: string; // e.g., Guru, Tendik
    readonly implementationSchedule: string;
  }>;
}
```

## 2. DOMAIN OWNERSHIP & LIFECYCLE
| Domain | Owner | Lifecycle | Source of Truth |
|---|---|---|---|
| `ImplementationSupport` | TPK / Kepala Sekolah | Annual | `PlanningIntelligenceEngine` (RKT) |
| `Monitoring` | Tim Penjaminan Mutu | Semester / Annual | `EvaluationService` |
| `Evaluation` | Kepala Sekolah | Annual | `RaporIntelligenceEngine` |
| `Reflection` | TPK / Stakeholders | Semester | `EvaluationService` |
| `FollowUp` | Kepala Sekolah | Continuous | `PlanningIntelligenceEngine` |
| `ProfessionalDevelopment` | TPK | Annual | `MasterData` / `PlanningIntelligenceEngine` |

## 3. ASSEMBLER CONTRACT
The Assembler (`KspDocumentAssembler`) is the sole orchestrator.
1. Collects knowledge from `EvaluationService`, `PlanningIntelligenceEngine`, `RaporIntelligenceEngine`, etc.
2. Constructs the strictly typed, deep-readonly `Bab4KnowledgePayload`.
3. Passes the payload to the `buildKspBab4Section` function.
4. The Builder is completely isolated from metadata, the workspace, registries, or services.

## 4. BUILDER CONTRACT
The BAB IV Builder (`KspBab4Structure`) acts as a pure function:
1. **Input:** `Bab4KnowledgePayload`
2. **Process:** Iterates over the domain objects and maps them to Canonical Blocks.
3. **Output:** An array of `DocumentBlock`s (Canonical Document representation).
4. **Constraints:** No service queries, no data calculations, no state mutation.

## 5. CANONICAL MAPPING
The payload maps cleanly to existing Canonical Blocks:
* **HEADING:** Main sections (Pendampingan, Evaluasi, Pengembangan Profesional).
* **PARAGRAPH:** Introductory texts or descriptive summaries (e.g., `latestRaporEducationSummary`).
* **LIST:** Bulleted strategies (`ReflectionDomain.mechanisms`, `FollowUpDomain.strategies`).
* **TABLE:** Tabular schedules (`ImplementationSupportDomain.programs`, `MonitoringDomain.activities`, `ProfessionalDevelopmentDomain.trainingPlans`).
* **ATTACHMENT:** Optional references to external instruments or detailed records.

## 6. REGISTRY READINESS
Each domain is structured to be decoupled from current engines, allowing seamless migration to future registries:
* `ImplementationSupportDomain` → **Planning Registry**
* `MonitoringDomain` → **Monitoring Registry**
* `EvaluationDomain` → **Evaluation Registry**
* `ReflectionDomain` → **Evaluation Registry**
* `FollowUpDomain` → **Planning Registry**
* `ProfessionalDevelopmentDomain` → **Professional Development Registry** (HR/Capacity Building)

## 7. FILES REQUIRING MODIFICATION (LATER)

## 8. RISK ASSESSMENT
* **Coupling Risk:** ZERO. The payload contract ensures strict decoupling between knowledge sourcing and document generation.
* **Schema Risk:** LOW. The payload is simple, immutable, and strictly mapped to canonical types.
* **Future-Proofing:** HIGH. Interfaces clearly map to future Registries.
